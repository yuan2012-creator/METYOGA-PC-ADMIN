## 3. 经营总览归档

### 模块定位

总部 / 投资人经营判断页。回答「这家店 / 这批店现在经营得怎么样、钱安不安全、下一步该盯什么」，不是运营执行台，也不是财务明细表。

### 核心解决的问题

- 多店经营健康一眼判断
- 确认收入、实收、预收负债、利润口径区分
- 现金安全是否低于 80% 安全线
- P0 / P1 风险是否进入处理队列

### 已完成页面区块

- 页面 header：门店 / 周期筛选 + 导出报告（toast 占位）
- **经营诊断** hero：结论、标签、证据摘要、安全线 80%
- **经营利润摘要**：利润率、同比、利润状态
- **确认收入 / 实收金额 / 预收负债 / 现金安全覆盖率** 四指标卡
- **风险处理队列**：fact / impact / 建议来源 / 处理按钮
- **经营利润趋势**（mock 趋势摘要）
- **课程交付摘要**
- **多店经营对比**：确认收入、实收、预收负债、经营利润、覆盖率；区分盈利店与亏损店

### 当前未建设内容

- 无右侧抽屉（按设计，经营总览以首屏判断为主）
- 多店「查看详情」、导出报告、证据链均为 toast 占位
- 无真实财务 API、无真实导出

### 关键口径

| 概念 | 说明 |
|------|------|
| 实收金额 | 当期实际到账现金，不等于确认收入 |
| 确认收入 | 按履约 / 耗课规则确认的经营收入 |
| 预收负债 | 会员已付但未履约部分，**不是收入** |
| 经营利润 | **确认收入 − 成本**，区别于实收现金 |
| 现金安全覆盖率 | 安全线 **80%**，低于则 P0 提示 |

### 后续建议

1. 多店详情二级页（单店钻取，仍保持判断页而非流水表）
2. 风险处理记录与闭环状态
3. 对接真实经营汇总接口（按门店 / 周期）
4. 导出报告真实逻辑（权限 + 异步任务）

**文件：** `components/v2/dashboard/DashboardV2Page.tsx`、`dashboardV2.viewModel.ts`、`dashboardV2.css`

## 4. 今日运营归档

### 模块定位

门店当天执行作战台。回答「今天课上发生什么、现在最急什么、谁要跟进」，不是周排课页，不是会员分析页。

### 核心解决的问题

- 今日课程时间轴与当前 / 下一节焦点
- 当日紧急任务与必须处理队列
- 会员提醒与本周内降级事项
- 快捷操作入口（含扫码核销）

### 已完成页面区块

- Header：门店、日期筛选；扫码核销（**ghost**，不抢主视觉）
- **今日课程时间轴**（主视觉）：当前关注 / 下一重点标记
- **当前最紧急** sidebar
- **快捷操作**：扫码核销、名单、异常等（扫码保留为当日工具入口）
- **今日简报**：到课、预约、异常等统计
- **今日必须处理**：P0 / P1 任务队列
- **今日会员提醒**：生日、续费、到店等
- **本周内处理**：降级展示，非当日主战场

### 关键边界

| 负责 | 不负责 |
|------|--------|
| 当天课程执行与异常 | 周排课决策（→ 课程与排课） |
| 当日任务分派提示 | 完整会员生命周期分析（→ 会员经营） |
| 门店作战简报 | 财务核算与资产处理（→ 财务与资产） |

- 扫码核销、补签、爽约、名单等均为 toast 演示
- 无抽屉

### 后续建议

1. 扫码核销真实逻辑（权限 + 课程场次校验）
2. 今日课程名单二级页
3. 补签 / 爽约 / 缺席处理工单
4. 会员提醒处理记录

## 14. 禁止回退规则

后续开发**不得**将 V2 母版退化为传统后台形态或违反业务口径：

### 页面形态禁止

1. 不要把**经营总览**改成数据表 / 报表堆砌
2. 不要把**今日运营**改成课程列表或课表
3. 不要把**会员经营**改成会员大表 / CRM 拨号盘
4. 不要把**课程与排课**改成普通周课表 CRUD
5. 不要把**师资与团队**改成员工通讯录
6. 不要把**财务与资产**改成收支流水表
7. 不要把**活动与获客**改成活动列表、海报库或群发后台
8. 不要把**系统设置**改成无结构的全量设置仓库

### 文案与能力禁止

9. 不要出现 **AI 推荐 / 智能推荐 / 自动推荐**
10. 不要出现 **自动群发 / 一键群发**
11. 不要出现「已真实发送 / 已真实审批 / 已真实退款」等误导文案
12. 不要显示会员**完整手机号、身份证、详细住址、银行账号**
13. 不要显示老师**工资、课时费明细**
14. 不要在首页大面积外显**合同编号、支付流水号**

### 口径禁止混淆

15. **实收金额 ≠ 确认收入**
16. **预收负债 ≠ 收入**
17. **经营利润 = 确认收入 − 成本**（≠ 实收）
18. **耗课点数 ≠ 现金**
19. **现金安全覆盖率安全线 = 80%**（不可默默改掉）

## 15. 下一阶段建议

按推荐优先级排序：

### 1. 二级页面规划（优先）

在母版首屏不动的前提下，为「会员名单、线索池、收支明细、操作日志、规则配置」等高频入口定义二级页信息架构与返回路径。避免每个模块各自发明列表页样式。

### 2. 真实接口字段设计

对接前先把 viewModel 字段与 `docs/MET_YOGA_ADMIN_*_CONTRACT.md` 契约对齐；按模块分批替换 mock，保持 UI 区块不变。

### 3. 权限与审批流设计

系统设置母版已预留权限 / 审批抽屉结构；需单独产出角色矩阵与审批节点表，再接入 API，避免先做页面后补权限洞。

### 4. 小程序三端数据联动设计

明确会员端、老师端、PC 各写哪些字段、谁审批、谁留痕；名下会员、线索承接、资产变更需有跨端状态机。

### 5. build chunk 拆分优化

当前单 bundle > 500kB warning；可按 `components/v2/*` 路由 lazy import，不影响母版 UI。

## 16. 交接给 Cursor / Codex 的注意事项

### Cursor 适合继续做什么

- 二级页面 UI 与交互
- 组件抽取与 CSS 微调（仍须遵守 token）
- 抽屉 / 表单 / 空态 / 加载态补充
- 按契约替换 mock 为 adapter 调用
- Bug 修复与视觉对齐

### Codex 适合继续做什么

- 目录与模块边界梳理
- 公共 hooks / drawer shell 组件复用
- 性能与 chunk 优化
- 类型与接口层严格化
- CI / build 与测试基建

### 共同原则

1. **不要推翻母版**：页面主线、模块定位、口径已在本文档确认；新功能应「叠加」而非「重做首屏」。
2. **不要由 AI 重造业务逻辑**：漏斗阶段、S0–S6、财务口径、三端边界以产品与本文档为准；AI 只实现已确认规格。
3. **新增功能前先确认闭环**：例如「线索成交 → 会员经营承接」必须同时定义 PC、会员端、消息触达（点对点，非群发）。
4. **改 viewModel 前先对口径**：mock 数据承载业务演示语义，替换真实数据时保持字段含义不变。
5. **禁止修改范围**：未明确要求时，不要动 `App.tsx` 路由主线、`index.css` 全局样式、`sidebarV2.config.ts` 导航集合。

### 验收基线

- `npm run build` 应能通过
- 8 个 V2 导航均可进入
- 抽屉可开闭、空态不白屏
- Header P1 修复与抽屉统一精修不回退
