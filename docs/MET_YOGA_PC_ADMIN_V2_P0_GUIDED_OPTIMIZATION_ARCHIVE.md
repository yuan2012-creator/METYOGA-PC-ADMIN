1. **顶部结论 Hero** — 一句话状态 + 关键证据 + 影响范围标签；
2. **优先动作队列** — P0/P1/P2，含影响、负责人、来源、建议动作；
3. **解释 / 分类区** — 用人话解释核心指标或按问题类型拆开；
4. **摘要区** — 保留原有能力但下沉，不再抢首屏；
5. **明细入口** — 轻量按钮 / 小卡，toast 占位二级页；
6. **抽屉保留** — 单对象详情、证据链、名单、异常处理不删除。

**不改：** 业务逻辑、路由、导航、角色切换机制、真实接口、其他 5 个一级页面代码。

## 4. P0 页面一：会员经营归档

- 生命周期、服务待办、销售跟进、人群匹配、风险图谱、重点会员并列；
- 店长 / 管家需要自己判断今天先处理谁；
- 服务和销售边界不够前置；
- S0–S6 虽然完整，但抢占第一屏理解成本。

### 4.2 优化后结构

当前 `MemberV2Page` 信息层级：

1. **会员经营结论** — Hero 卡：状态、结论文案、影响标签、关键证据；
2. **今日会员优先动作** — P0/P1/P2 处理队列；
3. **服务与销售队列** — 服务待办与销售跟进双栏分离；
4. **会员生命周期分布** — S0–S6 保留但下沉；
5. **精准人群匹配** — 强调点对点邀约，禁止群发；
6. **会员风险图谱** — 风险分类与承接说明；
7. **重点会员** — 降级为明细入口区，点击开会员详情抽屉。

### 4.3 关键变化

- 第一眼看到会员经营状态（健康 / 观察 / 预警）；
- 今日动作前置，店长 / 管家知道「先处理谁」；
- 服务待办和销售跟进分离，边界更清晰；
- S0–S6 保留完整但不再占首屏；
- 精准匹配继续强调点对点、非群发；
- 重点会员降级为明细入口，不再与判断层并列；
- 会员详情抽屉完整保留（概览、资产、服务记录、风险、跟进建议等）。

验收项：顶部结论 ✅ · 今日动作 ✅ · 服务/销售分离 ✅ · 生命周期下沉 ✅ · 抽屉可用 ✅ · 无 AI 推荐 / 自动群发 ✅ · `npm run build` 通过 ✅

## 5. P0 页面二：财务与资产归档

### 5.1 优化前问题

- 财务口径正确，但非财务角色理解成本高；
- 实收 / 确认收入 / 预收负债 / 经营利润虽然区分，但缺人话解释；
- 资产风险、退费 / 冻结 / 转卡、收入证据链分布较靠后；
- 门店矩阵偏重，容易抢首屏；
- 店长不知道本周先处理哪些财务事项。

### 5.2 优化后结构

当前 `FinanceV2Page` 信息层级：

1. **财务与资产健康结论** — Hero 卡；
2. **本周财务优先动作** — P0/P1/P2 队列；
3. **先看懂这几个数字** — 实收、确认收入、预收负债、经营利润人话解释；
4. **核心财务指标** — 四指标卡 + 现金安全覆盖率；
5. **会员资产风险队列** — 处理事项导向；
6. **退款 / 冻结 / 转卡处理** — 三栏变更队列，保留证据链意识；
7. **收入确认与耗课证据** — 收入确认摘要；
8. **门店财务健康矩阵** — 下沉，多店对比不再抢首屏；
9. **财务明细入口** — 轻量入口区。

### 5.3 关键变化

- **现金安全覆盖率 72% 低于 80%** 被明确解释为人话结论，不再只靠数字；
- 本周财务优先动作前置（退费证据链、高余额低耗课、冻结复核等）；
- 「先看懂这几个数字」区用人话解释四项核心口径；
- 会员资产风险队列更像处理事项，而非纯展示；
- 退费 / 冻结 / 转卡保留证据完整度与操作日志意识；
- 门店财务矩阵下沉至中后段；
- 原有资产详情抽屉、门店财务抽屉、收入证据抽屉保留。

### 5.4 验收结论

**财务与资产 P0 引导式优化完成，可以作为财务与资产一级页当前稳定版本。**

验收项：健康结论 ✅ · 优先动作 ✅ · 人话解释 ✅ · 口径不混淆 ✅ · 门店矩阵下沉 ✅ · 抽屉可用 ✅ · `npm run build` 通过 ✅

| 层级 | 职责 | 典型组件 |
|------|------|----------|
| 1. 顶部结论区 | 30 秒知道「好不好 / 预警什么」 | Hero 卡 + 状态标签 + 关键证据 |
| 2. 优先动作区 | 知道「今天 / 本周先做什么」 | P0/P1/P2 处理队列 |
| 3. 解释 / 分类区 | 知道「为什么 / 差在哪 / 怎么拆」 | 人话解释卡、问题分类卡 |
| 4. 摘要区 | 保留判断依据但不下沉理解成本 | 压缩版列表、lane 摘要、矩阵摘要 |
| 5. 明细入口 | 承接二级页，不在一级页展开大表 | 轻量按钮 / 小卡 + toast |
| 6. 抽屉 / 二级页 | 单对象详情与证据链 | 统一 `met-v2-drawer-*` |

### 8.2 各页面职责分工

| 页面类型 | 一级页职责 | 不应变成 |
|----------|------------|----------|
| **经营总览** | 多店 / 单店经营判断 | 报表流水 |
| **今日运营** | 当天执行与队列处理 | 课表 / 排课后台 |
| **会员经营** | 会员专项经营诊断 | 会员大表 |
| **课程与排课** | 课程供给与排课决策 | 排课 CRUD / 普通课表 |
| **师资与团队** | 师资供给与稳定性决策 | 员工通讯录 / 薪资表 |
| **财务与资产** | 财务健康与资产风险判断 | 收支流水表 |
| **产品与权益** | 产品规则与权益引擎 | 电商商品后台 |
| **活动与获客** | 获客漏斗与活动作战 | 海报素材库 |
| **系统设置** | 配置健康与控制中心 | 所有配置的大仓库 |

### 8.3 信息流向原则

```
一级页：判断 + 优先级 + 入口
    ↓
二级页：名单 + 明细 + 流程
    ↓
抽屉：单对象详情 + 证据链 + 轻量操作
```

- 一级页**不负责**完整 CRUD、完整报表、完整审批流；
- 二级页**负责**可翻页、可筛选、可批量处理的名单与流程；
- 抽屉**负责**当前选中对象的概览、证据、建议动作；
- 系统设置 / 产品与权益**负责**规则配置，但配置明细应逐步拆入二级页。

## 13. 后续 Cursor / Codex 执行建议

### 13.1 做什么

1. **先做二级页面规划文档**（`MET_YOGA_PC_ADMIN_V2_SECONDARY_PAGES_PLAN.md`），定清每页的 IA、字段、与一级页的入口关系；
2. **每次只做一个二级页面或一个模块**，避免再次「9 页齐改」；
3. **先定信息架构，再做 UI** — 名单页先定列、筛选、状态机，再画界面；
4. **接真实接口前对齐字段契约** — viewModel 结构应能平滑映射到 API 响应；
5. **权限与审批不能后补** — 二级页设计阶段就要预留角色可见性与操作边界。

### 13.2 不做什么

- **不要一次性继续改全部一级页面**；
- **不要在一级页继续堆更多信息** — 一级页职责是判断与入口；
- **不要在没有 IA 的情况下直接画二级页 UI**；
- **不要用 toast 永久替代二级页** — toast 是过渡，不是终态。

### 13.3 工具分工建议

| 工具 | 适合 |
|------|------|
| **Cursor** | 单页 UI 实现、交互、mock 数据、抽屉增强、CSS 精修 |
| **Codex** | 组件抽取、接口层、权限模块、性能优化、目录治理、类型契约 |

- **不要出现 AI 推荐**；
- **不要自动群发** — 补员、邀约必须强调点对点；
- **不要暴露敏感信息** — 会员隐私、薪资等；

- **不要混淆**实收、确认收入、预收负债、经营利润；

- 一级页必须保留「结论 → 动作 → 解释/分类 → 摘要 → 入口」层级；
- 已完成的 P0 四页**不得**回退到优化前并列区块结构；
