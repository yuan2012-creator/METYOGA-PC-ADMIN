# MET YOGA PC 后台｜真实数据源接入优先级设计 v1

> **目标**：在接入真实数据库 / 云函数前，明确**先接什么、后接什么、哪些长期可 mock**，以及**权限、审批、日志**的硬约束。  
> **说明**：文中「当前前端」路径以现有代码结构为准；接口形态（REST / GraphQL / BFF）由后续技术选型决定。

---

## 1. 接入原则

- **先接核心事实源，再接展示页**：先有会员、订单、场次、预约、签到、资产等**可追溯事实**，再驱动经营总览、数据中心、投资与合作授权的聚合展示。
- **先接只读查询，再接真实写入**：全链路先跑通「读模型 + 列表 + 详情 + 筛选」，再开放受控写入；避免 UI 已能点但后端无幂等与审计。
- **先接会员 / 订单 / 课程 / 资产，再接财务 / 权限 / 报表**：财务与报表依赖上游事实一致；权限与操作日志应在**第一批敏感写入前**具备最小可用，但**数据主表读接口**可早于完整 IAM 分批上线（见模块顺序）。
- **涉及钱、权益、合同、签到、退款、转卡、冻结、财务分录的操作，不能直接写库**：必须经过**身份权限校验 → 业务规则 → 必要审批 → 服务端事务/状态机 → 操作日志**；前端仅发起**意图**（草稿或申请单），禁止直连库表更新。

## 3. P1 第二批真实数据源

### Refund（退款）

| 项 | 说明 |
|----|------|
| **为什么不能第一批直接写** | 依赖支付事实、订单状态、资产余额与合同条款；错误写入直接造成资金与法务风险。 |
| **审批 / 日志** | 多级审批（金额阈值）、原路退回策略、操作日志、关联凭证。 |
| **模块联动** | `Mall` 退款抽屉、`Finance` 核销与闭环、会员资产、订单状态。 |

### AssetFreezeRecord（冻结记录）

| 项 | 说明 |
|----|------|
| **为什么不能第一批直接写** | 需与合同/订单/在途退款一致；否则冻结依据不足。 |
| **审批 / 日志** | 冻结/解冻审批、原因码、时效、日志。 |
| **模块联动** | `Mall` 冻结抽屉、会员资产状态、财务风险视图。 |

### AssetTransferRecord（转卡记录）

| 项 | 说明 |
|----|------|
| **为什么不能第一批直接写** | 涉及双会员/双店权益与收入归属，需完整证据链。 |
| **审批 / 日志** | 转出/转入确认、手续费规则、日志与通知。 |
| **模块联动** | `Mall` 转卡抽屉、会员资产、合同补充协议。 |

### Teacher（老师）

| 项 | 说明 |
|----|------|
| **为什么不能第一批直接写** | 人事主数据与课表/课时费耦合；误写影响薪酬与合规。 |
| **审批 / 日志** | 入转调离、资质变更走人事流程；日志必填。 |
| **模块联动** | `Staff`、课程场次、课时费、会员侧老师展示。 |

### TeacherSessionPay（老师课时费）

| 项 | 说明 |
|----|------|
| **为什么不能第一批直接写** | 依赖场次、签到、分成规则；与财务结算周期绑定。 |
| **审批 / 日志** | 结算批次、复核、锁定后不可改；日志。 |
| **模块联动** | `Finance` 课时费表、`Staff` 闭环、课程运营。 |

### FinanceLedger（财务分录）

| 项 | 说明 |
|----|------|
| **为什么不能第一批直接写** | 会计事实需借贷平衡、期间关闭、审计追踪。 |
| **审批 / 日志** | 制单 / 复核 / 过账分离；反冲与调整须审批。 |
| **模块联动** | `Finance` 全模块、订单/支付/退款/耗课。 |

### RuleConfig（规则配置）

| 项 | 说明 |
|----|------|
| **为什么不能第一批直接写** | 影响全系统计费、生命周期、排课；错误配置波及面大。 |
| **审批 / 日志** | 配置版本、生效时间、发布审批、回滚；全量日志。 |
| **模块联动** | `Settings`、会员生命周期、财务估算、课程结算。 |

### OperationLog（操作日志）

| 项 | 说明 |
|----|------|
| **为什么不能第一批直接写** | 日志应由服务端在每次敏感操作时**追加写入**，前端不「写日志表」。 |
| **审批 / 日志** | 与审计平台对接；保留不可篡改存储策略。 |
| **模块联动** | 全模块敏感操作。 |

### Role / Permission（权限角色）

| 项 | 说明 |
|----|------|
| **为什么不能第一批直接写** | 过早开放会导致越权访问真实数据或误操作批量写。 |
| **审批 / 日志** | 权限变更双人复核、紧急回收流程、全量日志。 |
| **模块联动** | `Settings`、IAM、所有写接口。 |

## 5. 模块接入顺序

1. **第一步：会员经营只读接入**  
   会员列表、详情、生命周期与风险只读；不写跟进也可先上线读。

2. **第二步：产品与合同只读接入**  
   商品、订单、合同、资产、支付/退款列表**只读**；替换 `Mall` 与 `MemberDetailModal` 数据源。

3. **第三步：课程运营只读接入**  
   课程库、场次日历、预约/签到列表只读；替换 `Courses` 与总览引用。

4. **第四步：预约 / 签到 / 耗课真实链路**  
   在只读稳定后，开放**服务端驱动**的预约创建、签到确认、耗课生成（禁止前端拼分录）。

5. **第五步：订单 / 支付 / 合同 / 资产真实链路**  
   下单、支付回调、合同签署驱动资产；后台以查询与异常处理为主。

6. **第六步：退款 / 冻结 / 转卡审批链路**  
   申请单 + 审批 + 状态机 + 与资产/订单/支付联动。

7. **第七步：财务分录 / 老师课时费 / 预收负债 / 确认收入**  
   在事实稳定后接会计引擎或财务中台；经营侧展示切换为「已结账期间」口径。

8. **第八步：权限角色 / 操作日志 / 审批流**  
   与所有写接口强制绑定；可部分能力提前于第七步上线最小集（见原则）。

9. **第九步：经营总览 / 数据中心 / 投资测算 / 合作授权聚合**  
   依赖前面只读与物化指标；默认只读聚合 API。

## 6. 写入边界（未来必须禁止「前端 / 普通角色直接写库」）

以下操作**不得**由前端或低权限角色直接更新数据库事实表；必须通过服务端、权限、审批与日志：

- 退款  
- 冻结  
- 转卡  
- 补签  
- 改签到  
- 改合同  
- 改资产  
- 改支付  
- 改财务分录  
- 改老师等级  
- 改员工权限  
- 导出数据（导出为受控任务，非随意 `SELECT *` 直连导出）
